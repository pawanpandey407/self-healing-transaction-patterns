# Pattern 3.2: Retry Storm Containment and Safe Replay

**Taxonomy entry:** Family 3, section 3.2 (retry storms and cascade amplification)
**Status:** v0

## Problem

When a component slows down or starts failing, the traffic aimed at it does not stay constant. Clients retry, internal services retry, schedulers rerun jobs, and humans resubmit. The struggling component now faces its normal load plus the retry load, which deepens the failure that caused the retries. The taxonomy calls this the amplifying shape: a small defect multiplied by the system's own behavior.

Retry storms have a second cost that gets less attention than the load amplification: unsafe replay. A retried request or a rerun job is only harmless if the system can tell what already happened. In payment processing, a rerun that cannot tell is how duplicates are born.

In my experience both costs are real. We ran ad hoc files with large numbers of records, and the memory and CPU configuration on the batch compute executors could not handle them; executors were getting killed partway through. Once we upgraded memory and reran the jobs, it worked fine. Around the same period, API applications that relied on an external vendor for chip feature processing were throwing back 4xx errors and were successful once retried. Both were found through email alerts and manual checking. Retrying was the recovery mechanism in every case, and it usually worked, which is exactly why nobody measured what the retries cost.

Who retried was a mix of everything: retry logic within the code that retried three times, fallback mechanisms behind that, and scheduled batch jobs on the workflow scheduler that had to be kicked off again manually. Under real overload the system used to break, and several pod restarts happened, which impacted overall runs. In some scenarios the system healed by itself and the job ran on retry automatically. Nothing in that list shed load on purpose. The system slowed down, fell over, restarted, and retried until it came back.

This pattern specifies two things: containment, so retry volume cannot amplify an existing failure, and safe replay, so the retries and reruns that do happen cannot create duplicates.

## Detection signal

The defining signature of a retry storm is divergence between two rates that normally track each other:

| Signature | Source | What it means |
|---|---|---|
| Arrival rate rising while unique-transaction rate is flat | Request counts vs distinct correlation ids | New work is not increasing; the same work is arriving repeatedly |
| Retry ratio per caller climbing | Attempt counter on each request | A specific caller has entered a retry loop |
| Scheduler reruns of partially completed jobs | Job history, run counts per job id | Replay risk window is open |
| Restart-driven rerun | Instance restart events followed by job restarts | The platform itself is generating retry load |

None of these signals exist unless every attempt is labeled. Two design rules make the signals possible:

1. **One correlation id for the life of the transaction.** The id is assigned at first attempt and carried unchanged through every retry, every hop, and every rerun. Retry attempts carry an attempt counter alongside it. First-attempt traffic and retry traffic must be distinguishable at every point in the pipeline, because load shedding needs to treat them differently.
2. **Retries are declared, not disguised.** A retry that presents itself as a fresh transaction defeats both detection and deduplication at once.

**Field note:** the second rule comes from watching the opposite in production. We had a unique identifier that we checked in the database, and if it already existed we passed a new value when we retried. The check was there to stop duplicates, and the workaround made every retry look like a brand new transaction. Debugging was pretty difficult in some scenarios because records carried similar data and there was no single correlation id that could track a transaction end to end.

## Decision policy

- **Retry budgets, enforced pipeline-wide.** Each caller gets a retry ratio budget (retries as a fraction of first attempts, over a sliding window). A caller that exhausts its budget has its retries rejected fast with a retry-after, while its first-attempt traffic continues. Budgets turn a retry storm from an unbounded amplifier into a bounded, observable overage.
- **Backoff with jitter is the policy default.** Immediate re-attempt in a loop is not permitted anywhere in the pipeline. Fixed three-attempts-and-stop, the default I saw most often in practice, is acceptable only with backoff between attempts.
- **Classify before retrying.** Deterministic rejections (validation failures, permanent declines) must not be retried at all; retrying them is pure amplification. Only transient classes (timeouts, throttling responses, 5xx) are retry-eligible.
- **Load shedding distinguishes attempt classes.** When the pipeline sheds load, retry traffic is shed first and first-attempt traffic is protected. Shedding first attempts to make room for retries inverts the priority of the business.
- **Replay requires proof of safety.** A job or batch that partially completed may only be rerun automatically if processing is idempotent: every record is checked against the correlation id of what already completed, and completed records are skipped. A rerun without that check requires a human decision, never an automatic trigger.

## Recovery action

1. Detect the divergence (arrival rate vs unique-transaction rate) or a budget overage and identify the retrying callers from attempt labels.
2. Enforce the budget: reject over-budget retries fast, with retry-after, keeping first-attempt traffic flowing.
3. For batch replay: reconcile first, then rerun only the records with no completed correlation id. The reconciliation output is a machine-readable verdict of what was skipped and why, published before the rerun starts.
4. Verify recovery by outcome: unique-transaction success rate restored to baseline, retry ratio decayed back under budget, and zero duplicate completions for any replayed work.

**Field note:** the cost of skipping step 3 is not theoretical. In one incident, a first run processed some records while others got stuck. When the job was reprocessed, the records that had already processed were processed again, creating duplicates. The same thing happened with downstream reports, which got generated twice and sent out to production facilities to print. It was a waste of resources and bad reporting, and containing it meant informing the production facility by email, manually, with data on what not to process. That email is this pattern's reconciliation verdict, done by hand at human speed. The automated version has to exist before the rerun happens, not after the duplicates are discovered.

## Failure injection scenario

The reference implementation demonstrates containment and safe replay against the synthetic transaction pipeline:

1. **Transient overload with naive retries.** Inject high latency into the settlement stage and add a caller that retries every failure immediately. Expected: arrival rate diverges from unique-transaction rate, the caller's retry budget trips, over-budget retries are rejected fast, and first-attempt success rate stays at baseline through the entire injection.
2. **Deterministic failure retried.** Raise the validation stage failure probability and point the same naive retrier at it. Expected: classification marks validation rejections non-retryable, retry volume stays flat, and the verdict identifies the caller retrying non-retryable failures.
3. **Partial batch replay.** Run a batch of synthetic transactions, kill the run midway, and rerun the batch. Expected: reconciliation skips every record with a completed correlation id, the rerun processes only the remainder, and the duplicate completion count is exactly zero. Rerunning without the reconciliation step must reproduce the duplicate defect, proving the check is what prevents it.

## Non-goals

- Fixing the underlying slowness or failure that triggered the retries. That is Family 1 and Family 2 territory; this pattern bounds the amplification while the root cause is handled.
- Circuit breaking as a full pattern. Breakers and retry budgets cooperate, but breaker design (thresholds, half-open probing) is its own document.
- Duplicate detection at the reporting and settlement layer for causes other than replay, such as upstream double-sends. This pattern guarantees only that retries and reruns it governs cannot create duplicates.
