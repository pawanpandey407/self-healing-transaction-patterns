# Pattern 5.1a: Fail-to-Start Deployment Gating

**Taxonomy entry:** Family 5, section 5.1 (bad deployment, fail-to-start mode)
**Status:** v0

## Problem

A release that never becomes healthy is the cheapest deployment failure to catch and the most embarrassing one to miss. The ways a rollout fails to start form a small, stable, known set: the image cannot be pulled, the process crashes on startup, readiness or liveness probes never pass, a secret-management init container fails to initialize, or the application cannot reach its database during startup. Every one of these is visible in the first minutes of a rollout and is mechanical to detect.

In my experience the actual detection mechanism is people. During rollouts I watched the pipeline myself, and once a release was live, developers were responsible for post-validation: checking real transactions coming in from clients to confirm the change worked. That is how I knew a release came up okay. When a deployment went wrong at startup, most of the time it was something wrong with the infrastructure itself, not the code, and recovery meant informing the SRE and network teams to check connections while I made the changes on my side in the deployment and configuration files. Every step of that loop runs at human speed. This pattern replaces the watching human with an automated gate: a deployment whose new instances cannot start halts and rolls itself back, no observer required.

This pattern covers only the fail-to-start mode. The release that starts but behaves badly is a separate pattern (canary analysis) with different signals and a different decision problem.

## Detection signal

The gate watches the new-version cohort of a rollout and classifies startup outcomes into two signal classes.

**Deterministic failures.** These cannot self-resolve and justify immediate action:

| Signature | Source | Typical visibility |
|---|---|---|
| Image pull failure | Orchestrator events (`ImagePullBackOff`, `ErrImagePull`) | Seconds |
| Init container failure (secret retrieval, config bootstrap) | Init container exit code, orchestrator events | Seconds to a minute |
| Immediate termination on start | Container exit before readiness, restart count rising | First restart cycle |

**Threshold failures.** These need a budget, because a slow start and a dead start look identical at first:

| Signature | Source | Gate condition |
|---|---|---|
| Crash loop | Restart count on new-version pods | Restart count reaches N (default 3) |
| Probes never passing | Readiness state over time | Not ready within the startup deadline |
| Database connectivity failure on startup | Application startup logs, connection errors before ready | Folded into the startup deadline; the symptom is "never ready" |

Two design rules keep the signal honest:

1. **A declared startup deadline per service.** Each service states its worst-case legitimate startup time (large application contexts and cache warmup can take minutes). The gate measures against the declared deadline, not a global constant, so a slow-but-fine start is never punished. Kubernetes startup probes exist for exactly this reason and the deadline should agree with them.
2. **Cohort scope.** Only new-version instances are evaluated. Old-version instances continuing to serve is expected and is not evidence of anything.

**Field notes:** two incidents from my own deployments shaped the rules above. First, a secret-management init container repeatedly failing during rollout because of connection issues between the cluster and the secrets backend. It was a canary deployment, so it rolled back automatically when the new instances failed; nothing was wrong with the code, the path to the secrets was. That rollback machinery is the closest thing to this pattern I have seen running in production, and the gap it left is exactly what this document specifies: the rollback happened, but the diagnosis still had to be assembled by humans afterward, checking the deployment logs first and then the application logs to work out why the release failed. The verdict this pattern emits is that dig, automated. Second, applications failing their startup health checks and never coming ready, fixed by raising the probe's initial delay from one minute to four minutes. That second incident is the whole argument for the declared startup deadline: the application was fine, the deadline was wrong, and a gate built on a global one-minute assumption would have punished every legitimately slow start we had.

## Decision policy

- On any deterministic failure in the new cohort: halt the rollout immediately. Do not wait for remaining instances to fail the same way; an unpullable image will not become pullable on the next pod.
- On a threshold failure: halt when the first new-version instance crosses its threshold (restart count N, or startup deadline exceeded).
- After halting, decide rollback versus hold:
  - **Default: automatic rollback** to the last known-good version.
  - **Exception: hold, do not roll back** when the release is flagged as carrying an irreversible change, the classic case being a database schema migration the previous version cannot run against. Releases declare this flag in deployment metadata. A flagged release halts, keeps old instances serving where the orchestrator still has them, and pages a human instead of rolling back into a different failure.
- Every gate decision emits a machine-readable verdict: the triggering signature, the instance evidence (events, exit codes, restart counts), and the action taken. The deployment is marked failed with that verdict attached, so the postmortem starts with the diagnosis already written.

The policy is deliberately conservative in one direction only: it never lets a rollout that cannot start continue to consume the fleet. It is not permitted to be conservative in the other direction, because "keep waiting and see" is exactly the human behavior being replaced, and fail-to-start modes silently reduce serving capacity while everyone waits.

## Recovery action

1. Halt the rollout: stop creating new-version instances.
2. If rollback is permitted (no irreversible-change flag): restore the last known-good version and scale it back to full capacity.
3. Verify recovery by outcome, not by component health: fleet readiness restored to pre-rollout count, and transaction throughput and success rate back at the pre-rollout baseline. A rollback that restores green pods but not transaction flow has not recovered.
4. Publish the verdict (signature, evidence, action) to the same channel used for all pipeline events, with paging-grade delivery for anything that reduced serving capacity. Email-only delivery is a taxonomy-documented failure mode of its own.

## Failure injection scenario

The reference implementation demonstrates the full loop with three injected fail-to-start cases against the synthetic transaction pipeline:

1. **Bad image tag.** Deploy a version referencing a nonexistent image tag. Expected: deterministic signature within seconds, immediate halt, rollback, throughput unaffected.
2. **Crash on startup.** Deploy a build that throws during application startup. Expected: restart count climbs, gate trips at N restarts, rollback, verdict shows the exit evidence.
3. **Unreachable database on startup.** Deploy with database connection settings pointing at a closed port. Expected: instances never become ready, gate trips at the startup deadline, rollback, verdict distinguishes "never ready" from "crash loop".

Each scenario passes only if the synthetic transaction success rate never drops below baseline during the entire injection, which is the point of the pattern: a deployment that cannot start should be invisible to the traffic.

## Non-goals

- Behavioral regression detection (error rate or latency divergence between version cohorts). That is the canary analysis pattern for the starts-but-misbehaves mode of 5.1.
- Configuration drift outside the deployment pipeline (taxonomy 5.2).
